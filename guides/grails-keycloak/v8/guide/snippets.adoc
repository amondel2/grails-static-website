== Understanding the Code

This section explains the key components that wire Keycloak authentication into your Grails application. If you're new to Keycloak or Grails, read this section carefully—each class solves a specific problem in the authentication flow.

=== How Keycloak and Grails work together

Before diving into the code, here's what happens when a user logs in:

1. User clicks a protected link in your Grails app and isn't logged in.
2. The app redirects to Keycloak's login page (on a different server).
3. User enters their username and password into Keycloak's login form.
4. Keycloak validates the credentials and issues a security token (JWT) containing the user's identity and roles.
5. Keycloak redirects back to your Grails app with the token.
6. The Grails app receives the token and needs to extract the user's information and roles from it.
7. Spring Security (a framework that Grails uses) stores this info so pages and controllers can check "is this user logged in?" and "does this user have the ADMIN role?"

The three classes below handle steps 6 and 7.

=== SecurityConfig: The gatekeeper

SecurityConfig tells Spring Security which URLs anyone can access without logging in, and which ones require login. It also configures how Keycloak tokens are processed.

include::../snippets/src/main/groovy/com/grails/example/SecurityConfig.groovy[]

**What it does:**

* `@Configuration` marks this as a Spring configuration class—Spring reads it on startup and applies these rules.
* `.permitAll()` on `/`, `/assets/**`, etc. means anyone can visit these URLs without logging in (public pages).
* `.anyRequest().authenticated()` means **every other URL requires the user to be logged in**. If they're not, they're sent to Keycloak.
* `.oauth2Login()` tells Spring Security to accept logins via OAuth2/OIDC (the protocol Keycloak uses). This is the "bridge" that lets Keycloak handle passwords.
* `userAuthoritiesMapper(keycloakAuthoritiesMapper)` is the key line: after the user logs in and Keycloak sends back their info, this tells Spring Security to run the `KeycloakAuthoritiesMapper` to extract the user's roles.
* `.logout()` configures logout to tell Keycloak the user is leaving, not just delete the local session.

=== KeycloakAuthoritiesMapper: Translating roles into permissions

When Keycloak sends back the user's info, it includes a JWT token with a claims section. That claims section contains roles, but they're formatted in a way Keycloak understands—not in a way Spring Security understands. This class translates them.

include::../snippets/src/main/groovy/com/grails/example/KeycloakAuthoritiesMapper.groovy[]

**What it does:**

The Keycloak JWT token contains a section called `resource_access.<clientId>.roles`. For example:

```json
{
  "resource_access": {
    "my-app": {
      "roles": ["USER", "ADMIN"]
    }
  }
}
```

* `init()` reads your app's Keycloak client ID from `application.yml`. (The client ID identifies your Grails app to Keycloak.)
* `mapAuthorities()` iterates over all the authorities Spring Security found in the token.
* For each OIDC authority (the token sent by Keycloak), it calls `addKeycloakRoles()`.
* `addKeycloakRoles()` digs into the `resource_access.<clientId>.roles` section, extracts each role, and converts it to Spring Security's format: `ROLE_<NAME>` (e.g., `ROLE_USER`, `ROLE_ADMIN`).
* Spring Security now understands these roles and can enforce them. For example, a controller can say `@PreAuthorize("hasRole('ROLE_ADMIN')")` to allow only admins.

**Why does this matter?**

Without this mapper, Keycloak's roles stay in Keycloak's format and Spring Security doesn't recognize them. Your app has the user's info but can't check their roles. This class is the translator.

=== SecurityTagLib: Checking permissions in web pages (GSP views)

In Grails, web pages are written in GSP (Groovy Server Pages). SecurityTagLib provides simple tags you can use in GSP to show or hide content based on whether the user is logged in or has a certain role.

include::../snippets/grails-app/taglib/com/grails/example/SecurityTagLib.groovy[]

**What the tags do:**

* `<app:loggedIn>...content...</app:loggedIn>` — Shows the content only if the user is logged in.
  ```groovy
  <app:loggedIn>
      Welcome back! <app:currentUser>{ user -> ${user.firstName} }</app:currentUser>
  </app:loggedIn>
  ```

* `<app:ifNotLoggedIn>...content...</app:ifNotLoggedIn>` — Shows the content only if the user is **not** logged in. Useful for showing a "Log in" link.
  ```groovy
  <app:ifNotLoggedIn>
      <a href="/login">Click here to log in</a>
  </app:ifNotLoggedIn>
  ```

* `<app:hasRole role="ADMIN">...content...</app:hasRole>` — Shows the content only if the user has that role.
  ```groovy
  <app:hasRole role="ADMIN">
      <a href="/admin">Admin panel</a>
  </app:hasRole>
  ```

* `<app:currentUser>{ user -> ... }</app:currentUser>` — Extracts the current user's details (username, first name, last name, email) from Keycloak and passes them to the code block.
  ```groovy
  <app:currentUser>{ user ->
      Email: ${user.email}
  }</app:currentUser>
  ```

**How it works:**

* Each tag checks `SecurityContextHolder.context.authentication` — this is where Spring Security stores the logged-in user's information.
* If `authentication` is null or the user is anonymous, the user is not logged in.
* If `authentication` exists and is authenticated, the user is logged in.
* For role checks, the code looks at `authentication.authorities` — a collection of roles that was populated by the `KeycloakAuthoritiesMapper` above.
* If the user has the requested role, the tag's content is rendered.

**Example use in a GSP page:**

```groovy
<%@ page contentType="text/html;charset=UTF-8" %>
<!DOCTYPE html>
<html>
  <head><title>My App</title></head>
  <body>
    <app:ifNotLoggedIn>
        <p>You are not logged in. <a href="/login">Log in here</a></p>
    </app:ifNotLoggedIn>
    
    <app:loggedIn>
        <p>Welcome, <app:currentUser>{ user -> ${user.firstName} }</app:currentUser>!</p>
        
        <app:hasRole role="USER">
            <p>You can see user content.</p>
        </app:hasRole>
        
        <app:hasRole role="ADMIN">
            <p><a href="/admin">Go to admin panel</a></p>
        </app:hasRole>
    </app:loggedIn>
  </body>
</html>
```

=== Putting it all together

The flow is:

1. **User visits a protected URL** → SecurityConfig sees it requires authentication.
2. **User is sent to Keycloak** → User logs in with username/password.
3. **Keycloak sends back a token** → Token contains user's roles in Keycloak's format.
4. **KeycloakAuthoritiesMapper translates roles** → Converts `resource_access.my-app.roles` into Spring Security's `ROLE_*` format.
5. **SecurityTagLib checks permissions in views** → GSP pages use `<app:loggedIn>`, `<app:hasRole>`, etc. to show/hide content.
6. **Controllers use `@PreAuthorize`** → Server-side methods can require specific roles too.

All three pieces work together to give your app a complete authentication and authorization system powered by Keycloak.
